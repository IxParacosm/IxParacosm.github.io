# 4. Backend and storage options

_Research topic: Storage/backend options for the hq.jwcoconsulting.com Avatar Kit module (Cloudflare-hosted hash-routed SPA, solo operator with Claude Code): Cloudflare D1/R2/KV/Access vs Supabase vs Apps Script+Sheets vs Git-as-DB vs Firebase/PocketBase/Airtable, plus Google Sheets ingestion and sync strategy_

## Summary

METHOD NOTE: the egress proxy blocks developers.cloudflare.com, supabase.com, developers.google.com, docs.github.com, firebase, airtable, pocketbase.io and core.telegram.org. I verified Cloudflare, GitHub, Supabase and PocketBase facts by reading the SOURCE of those doc pages from their public GitHub repos (raw.githubusercontent.com: cloudflare/cloudflare-docs, github/docs + github/rest-api-description OpenAPI, supabase/supabase, pocketbase/pocketbase) and the Sheets v4 discovery document from googleapis.com. Those are marked 'verified' and cite the rendered doc URL. Google Apps Script, gviz, Firebase, Airtable and Zero-Trust-plan facts come only from search-engine summaries of the official pages and are marked 'likely'. Telegram facts come from a third-party machine-readable mirror of the Bot API page (Bot API 10.3) and are marked 'likely'.

SCORED COMPARISON (1 = bad, 5 = best; criteria: Cost / Setup effort / Image storage / Auth / Telegram-bot hosting / Claude-Code-friendliness / Lock-in = total/35)
1. Cloudflare Workers (static assets, or existing Pages + Functions) + D1 + R2 (+KV) + Cloudflare Access: 5 / 3 / 5 / 5 / 5 / 5 / 3 = 31. $0 at this scale (D1 free: 5M rows read + 100k rows written per day, 5 GB; R2 free: 10 GB + 1M Class A + 10M Class B ops per month, zero egress; Workers free 100k req/day; Access OTP email login, free up to 50 users). Everything lives in one repo and deploys with `wrangler deploy`; local dev with `wrangler dev`; D1 is SQLite with `wrangler d1 export` and 30-day Time Travel. Telegram webhook and cron jobs run in the same Worker (free plan: 5 cron triggers, 10 ms CPU per invocation; paid $5/mo: 30 s default CPU, 250 crons). Lock-in is moderate: D1 exports to plain SQL, R2 is S3-compatible, but Access JWT validation and bindings are Cloudflare-specific.
2. Supabase (Postgres + Storage + Auth + Edge Functions): 4 / 4 / 4 / 4 / 3 / 4 / 4 = 27. Free: 500 MB DB, 1 GB storage (50 MB max file), 500k edge invocations, 50k MAU, 2 projects — BUT 'Free projects are paused after 1 week of inactivity' (verified in the pricing data file), which is fatal for a sporadically used admin tool unless you pay Pro ($25/mo, includes $10 compute credit = one Micro instance). Telegram bot would live in an Edge Function (Deno, 256 MB, 150 s wall clock on free) separate from the Cloudflare-hosted site; CORS and a second dashboard to maintain.
3. Google Apps Script web app + the existing Sheet as DB + Drive for images: 5 / 3 / 2 / 2 / 3 / 2 / 3 = 20. Free and the Sheet already exists, but: web-app POSTs answer with a 302 redirect that clients must follow; you cannot set CORS headers (browser calls must be 'simple' requests, e.g. text/plain bodies, or no-cors); 'Execute as Me + Anyone' makes the URL itself the credential; Drive image hotlinks (uc?export=view) are unreliable/403 in 2025; consumer quotas (6 min per execution, 20k UrlFetch/day, 90 min trigger runtime/day). Fine as a sync bridge (installable onEdit trigger -> webhook), poor as the primary backend.
4. 'Git as database' (JSON in IxParacosm.github.io edited via GitHub Contents API, served by GitHub Pages): 5 / 4 / 2 / 1 / 1 / 5 / 5 = 23 but DISQUALIFIED for the accounts registry: GitHub Pages sites are public, so account logins/VA data would be world-readable; a PAT with Contents:write would sit in the browser (fine-grained PATs max 1-year lifetime, full write to the repo); no server for Telegram webhooks (only Actions cron); Contents API PUT needs the current blob `sha` (concurrent edits conflict) and is capped at 100 MB per file; Pages soft limits 1 GB site, 100 GB/mo bandwidth, 10 builds/hr; Pages ToS says it is not for running your online business. Keep it ONLY for the clickable prototype with sample JSON.
5. Firebase (Firestore + Storage): 4 / 3 / 3 / 4 / 3 / 3 / 2 = 22. Firestore free tier is generous (1 GiB, 50k reads/20k writes per day, likely) but Cloud Storage for Firebase now requires a Blaze (billing-enabled) project for new buckets (likely, Feb 2026 change); Firestore is a proprietary NoSQL model (poor fit for the SQL-ish accounts/kits joins and for Claude writing migrations). PocketBase: 4 / 3 / 4 / 4 / 4 / 4 / 4 = 27 technically excellent (single Go binary, SQLite, files local or S3, auth, admin UI, JS hooks) but self-hosted on a VPS (~$4-12/mo, you own backups/updates) and the README warns backward compatibility is not guaranteed before v1.0. Airtable: 2 / 5 / 3 / 4 / 2 / 3 / 2 = 21: free plan 1,000 records/base and 1,000 API calls/month (likely) — hundreds of accounts x kits x assignments plus a UI that polls will exhaust it; attachment URLs expire after ~2 hours so you cannot hotlink kit images; Team is $20/seat/mo.

RECOMMENDATION: Cloudflare all-in (Worker with static assets, or Pages + /functions if hq is already a Pages project) + D1 + R2 + Access (OTP) — score 31/35, $0/month until you want >10 ms CPU or cron-heavy jobs, then $5/month Workers Paid. Cloudflare's own docs now say 'Start new projects with Workers' (Pages is maintained but Workers is the primary platform); since hq.jwcoconsulting.com is already behind Cloudflare, first check whether it is a Pages project or a Worker and keep that; the code shape (`functions/api/[[route]].js` vs `src/index.ts` fetch handler) is the only difference and bindings are identical.

SHEET STRATEGY: Keep the Google Sheet as the short-term source of truth for the ACCOUNTS roster (the VAs already edit it), import it one-way into D1 via the Sheets API v4 with a service account (share the sheet with the service-account email; the Worker signs an RS256 JWT with WebCrypto and exchanges it at oauth2.googleapis.com/token; GET v4/spreadsheets/{id}/values/{Sheet!A1:ZZ}), on a cron trigger plus a 'Sync now' button. Do NOT use publish-to-web CSV or gviz for this data: both require the sheet to be link-shareable (public to anyone with the URL) and publish-to-web is cached for minutes. Row identity: add a hidden `account_id` column (UUID) that the Worker writes back with values:update for rows lacking one (Sheets developer metadata is the API-native alternative that survives inserts/sorts). Kits, images, assignments and video jobs are born in D1/R2 from day one (never in the sheet). After one or two months, when VAs receive kits via Telegram and can log into Access-protected pages (50 free seats cover them), flip: D1 becomes the source of truth and the Worker writes a read-only mirror tab to the sheet.

MIGRATION PATH (prototype -> real backend):
Phase 0 (now, in IxParacosm.github.io): static SPA with `data/kits.json`, `data/accounts.json`, `data/vas.json`, `data/kit_types.json`; one `api.js` adapter exposing `listKits()/getKit(id)/saveKit(kit)/listAccounts()/assignKit()`; in prototype mode it reads the JSON and persists edits to localStorage. Kit type = a JSON schema document (`transformation` requires 6 images with roles before_1..after_3; `heygen` requires 1-3 images with role `reference`), so new kit types are data, not code.
Phase 1 (same repo, deployed to Cloudflare): add `wrangler.toml` with `[[d1_databases]] binding="DB"`, `[[r2_buckets]] binding="KITS"`, `[vars] TEAM_DOMAIN`, `POLICY_AUD`; `npx wrangler d1 create hq`, `migrations/0001_init.sql` (tables: kit_types, kits, kit_images, accounts, vas, kit_assignments, video_jobs, sync_runs, telegram_messages); routes `/api/kits`, `/api/kits/:id/images` (PUT body streams into `env.KITS.put('kits/{kit_id}/{image_id}.jpg')`), `/img/*` (GET from R2 behind Access), `/api/accounts`, `/api/assignments`, `/api/sync/sheet`, `/api/telegram/webhook`, `/api/telegram/send-kit`. Put an Access self-hosted application on hq.jwcoconsulting.com with a One-time PIN identity provider and an Allow policy for your email; validate `Cf-Access-Jwt-Assertion` in the Worker with `jose` (`createRemoteJWKSet(TEAM_DOMAIN + '/cdn-cgi/access/certs')`, issuer = TEAM_DOMAIN, audience = POLICY_AUD); add an Access Bypass policy for `/api/telegram/webhook` and verify `X-Telegram-Bot-Api-Secret-Token` there instead. Secrets via `npx wrangler secret put TELEGRAM_BOT_TOKEN / ONEUP_API_KEY / GOOGLE_SA_KEY`. Seed D1 from the prototype JSON with `wrangler d1 execute hq --remote --file=seed.sql`. Swap `api.js` to fetch `/api/*`.
Phase 2: Sheet import cron (`triggers.crons = ["0 */6 * * *"]`), OneUp `listsocialaccounts` pull into `accounts.oneup_account_id`, Telegram `sendMediaGroup` (2-10 items, same type) for kit delivery, storing returned `file_id`s in `kit_images.telegram_file_id` so re-sends are free and size-unlimited.
Phase 3: video jobs table + per-model adapters (same 'type as data' pattern as kit types), Workers Paid ($5) only when cron/CPU needs exceed free limits.

## Facts

- **verified** D1 Workers Free plan: 5 million rows read / day, 100,000 rows written / day, 5 GB storage total; Workers Paid: first 25 billion rows read / month then $0.001 per million, first 50 million rows written / month then $1.00 per million, first 5 GB then $0.75 / GB-month. Free limits reset daily at 00:00 UTC. Rows read counts rows SCANNED (a full table scan of 5,000 rows = 5,000 rows read); indexes reduce it. ([source](https://developers.cloudflare.com/d1/platform/pricing/))
- **verified** When a Free account hits the daily D1 read/write limit, queries fail with errors until reset; at the storage limit you must delete data before inserting. Upgrading to Workers Paid removes these limits 'typically within minutes'. D1 charges no egress. ([source](https://developers.cloudflare.com/d1/platform/pricing/))
- **verified** D1 limits: 10 databases per account (Free) / 50,000 (Paid); max database size 500 MB (Free) / 10 GB (Paid); account storage 5 GB (Free) / 1 TB (Paid); Time Travel 7 days (Free) / 30 days (Paid); 50 queries per Worker invocation (Free) / 1000 (Paid); 100 columns per table; 2 MB max row/BLOB; 100 KB max SQL statement; 100 bound parameters per query; 30 s max query duration; `d1 execute --file` import up to 5 GB. ([source](https://developers.cloudflare.com/d1/platform/limits/))
- **verified** D1 Time Travel is always on, costs nothing, and restores a database to any minute within the retention window; `wrangler d1 info <db>` shows `version: production` for databases that support it. ([source](https://developers.cloudflare.com/d1/reference/time-travel/))
- **verified** Export/import D1 with `npx wrangler d1 export <db> --remote --output=./database.sql` (flags `--table=`, `--no-data`) and `npx wrangler d1 execute <db> --remote --file=./file.sql` (use `--local` for the local dev database; `--command="SELECT ..."` for ad-hoc SQL). ([source](https://developers.cloudflare.com/d1/best-practices/import-export-data/))
- **verified** R2 pricing (Standard): $0.015 / GB-month, Class A ops $4.50 / million, Class B ops $0.36 / million, egress free. Free tier per month: 10 GB-month storage, 1 million Class A, 10 million Class B. Class A includes PutObject, CopyObject, ListObjects, multipart ops; Class B includes GetObject, HeadObject; DeleteObject is free. Usage is rounded UP to the next billing unit (1.1 GB-month bills as 2 GB-month). ([source](https://developers.cloudflare.com/r2/pricing/))
- **verified** R2 limits: unlimited objects/storage per bucket, 1,000,000 buckets per account, object key 1,024 bytes, object metadata 8,192 bytes, 5 GiB single-part upload (4.995 TiB multipart), max 1 concurrent write per second to the same key, 100 custom domains per bucket. ([source](https://developers.cloudflare.com/r2/platform/limits/))
- **verified** R2 buckets are private by default; a bucket can be exposed on a custom domain under your Cloudflare zone (with Cache, WAF) or an r2.dev subdomain for non-production use; public buckets do not list contents at the root. To restrict a custom-domain bucket to teammates use Cloudflare Zero Trust Access (tutorial 'Protect an R2 Bucket with Cloudflare Access') and disable the r2.dev URL. ([source](https://developers.cloudflare.com/r2/buckets/public-buckets/))
- **verified** R2 presigned URLs (S3 SigV4) grant a single GET/PUT/HEAD/DELETE on one object for 1 second to 7 days (604,800 s); generated server-side with an R2 API token (Access Key ID/Secret) and an S3-compatible SDK, no call to R2 needed. ([source](https://developers.cloudflare.com/r2/api/s3/presigned-urls/))
- **verified** From a Worker, R2 is used through a bucket binding: `await env.MY_BUCKET.put(key, request.body, { httpMetadata: request.headers })` and `const object = await env.MY_BUCKET.get(key)` (null if missing); configured as `[[r2_buckets]] binding = "MY_BUCKET" bucket_name = "..."`. ([source](https://developers.cloudflare.com/r2/api/workers/workers-api-usage/))
- **verified** Workers KV pricing: Free plan 100,000 keys read / day, 1,000 keys written / day, 1,000 deletes / day, 1,000 list requests / day, 1 GB stored (limits reset 00:00 UTC; exceeding one makes that operation type fail). Paid: 10 million reads/month then $0.50/million; 1 million writes, deletes and lists/month then $5.00/million; 1 GB then $0.50/GB-month. Dashboard and wrangler operations count as billable usage. ([source](https://developers.cloudflare.com/kv/platform/pricing/))
- **verified** Workers Free plan: 100,000 requests per day, 10 ms CPU time per invocation, 50 subrequests per request, 5 Cron Triggers per account, 100 Workers per account, 64 env vars per Worker. Workers Paid: minimum $5 USD per month per account, 10 million requests/month included then $0.30 per additional million, 30 million CPU-ms/month included then $0.02 per million CPU-ms, up to 5 minutes CPU per invocation (default 30 s), 10,000 subrequests per request, 250 Cron Triggers, 500 Workers. Pages Functions are billed exactly as Workers. Requests to static assets are free and unlimited. Memory 128 MB on both plans. ([source](https://developers.cloudflare.com/workers/platform/pricing/))
- **verified** Workers request body size depends on the Cloudflare zone plan: 100 MB (Free and Pro), 200 MB (Business), up to 5 GB (Enterprise); exceeding it returns 413. Response body size has no enforced limit. CPU time per Cron Trigger: 10 ms on Free; on Paid 30 s for intervals under 1 hour and 15 min for intervals of 1 hour or more. Only 6 outgoing connections may be waiting for response headers at once. ([source](https://developers.cloudflare.com/workers/platform/limits/))
- **verified** Cloudflare's Pages docs carry a banner: 'Are you sure you want to use Pages? Workers supports most Pages use cases and offers a broader feature set. It is Cloudflare's primary platform for building applications. Start new projects with Workers.' The migration guide states static-asset requests are free on Workers too, Pages Functions invocations cost the same as Workers, and Workers adds Durable Objects, Cron Triggers and better observability. ([source](https://developers.cloudflare.com/workers/static-assets/migration-guides/migrate-from-pages/))
- **verified** Pages Functions: put files in a `/functions` directory at the project root (not in the static output dir); `export function onRequest(context)` (or onRequestGet/onRequestPost) must return a Response; file path = route (`functions/api/kits.js` -> `/api/kits`); `[param].js` matches one segment, `[[catchall]].js` matches any depth, values in `context.params`; unmatched routes fall back to static assets. Bindings (KV, R2, D1, env vars, secrets) are added in dashboard Settings > Bindings or in the wrangler config and read from `context.env`. Direct Upload from the dashboard does not support Functions; deploy via Git integration or wrangler. ([source](https://developers.cloudflare.com/pages/functions/routing/))
- **verified** Cloudflare Pages limits (Free): 1 concurrent build, 500 builds/month, 20-minute build timeout, 20,000 files per site, 25 MiB max per asset (use R2 public buckets for larger files), 100 projects per account, unlimited preview deployments. ([source](https://developers.cloudflare.com/pages/platform/limits/))
- **verified** Cron Triggers run on UTC, require a `scheduled(controller, env, ctx)` handler, and are declared in wrangler config as `"triggers": { "crons": ["*/3 * * * *", "0 15 1 * *"] }`; deploying replaces previous crons, an empty array removes them all. ([source](https://developers.cloudflare.com/workers/configuration/cron-triggers/))
- **verified** Secrets are set with `npx wrangler secret put <KEY>` (creates and deploys a new Worker version immediately) or `wrangler versions secret put`; they are only readable programmatically via `env`. ([source](https://developers.cloudflare.com/workers/configuration/secrets/))

- **verified** Cloudflare Access adds the application token as the `Cf-Access-Jwt-Assertion` request header (and a `CF_Authorization` cookie for browser requests); validate the header, not the cookie. Public keys live at `https://<team>.cloudflareaccess.com/cdn-cgi/access/certs` (`keys` JWKS, `public_certs`); signing keys rotate every 6 weeks with the previous key valid 7 more days, so fetch keys at runtime and match by `kid`. Each Access application has a fixed AUD tag (Zero Trust > Access controls > Applications > Configure > Application Audience (AUD) Tag) that is the `aud` claim; the docs' Worker example uses `jose` `jwtVerify(token, createRemoteJWKSet(new URL(`${TEAM_DOMAIN}/cdn-cgi/access/certs`)), { issuer: TEAM_DOMAIN, audience: POLICY_AUD })` with env vars POLICY_AUD and TEAM_DOMAIN. ([source](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/))
- **verified** Access application token claims include `aud`, `email` (verified by the IdP), `exp`, `iat`, `nbf`, `iss` (team domain URL), `type` ('app' or 'org'), `identity_nonce`, `sub` (stable per email per account; changes if the user is removed and re-added), `country`. Full identity (idp data, groups, user_uuid) is available by sending the CF_Authorization cookie to `https://<team>.cloudflareaccess.com/cdn-cgi/access/get-identity`. ([source](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/))
- **verified** Cloudflare Access One-time PIN sends a login code to approved email addresses as an alternative to an IdP; new Zero Trust orgs default to the Cloudflare identity provider and OTP must be added manually (Zero Trust > Integrations > Identity providers > Add > One-time PIN, or API POST /accounts/{account_id}/access/identity_providers with type 'onetimepin'). ## Recommendations

- Choose Cloudflare end-to-end: Worker (static assets) or existing Pages + `/functions`, D1 for kits/accounts/assignments/jobs, R2 for kit images, Cloudflare Access (One-time PIN) for login. It scores 31/35, costs $0 at this scale, and keeps UI + API + bot + cron in one repo that Claude Code can run locally with `wrangler dev` and deploy with one command.
- First determine how hq.jwcoconsulting.com is deployed (Cloudflare dashboard > Workers & Pages). If it is a Pages project, add `functions/api/[[route]].js` and bindings; if it is a Worker with static assets, add routes to its fetch handler. Do not migrate Pages->Workers just for this; Cloudflare only recommends Workers for NEW projects.
- Put Cloudflare Access in front of the whole hostname (self-hosted app, OTP IdP, Allow policy = your email now, VA emails later; 50 free seats). In the Worker, verify `Cf-Access-Jwt-Assertion` with `jose` against `<team>.cloudflareaccess.com/cdn-cgi/access/certs`, issuer and AUD pinned, and read `payload.email` for authorship/role checks. Add a Bypass policy only for `/api/telegram/webhook` and gate that route with the `X-Telegram-Bot-Api-Secret-Token` header.
- Serve kit images through the Worker (`GET /img/kits/{kit_id}/{image_id}` -> `env.KITS.get(key)`) so Access protects them, or bind R2 to a custom domain (e.g. kits.hq.jwcoconsulting.com) protected by the same Access app; use the r2.dev URL only for dev. Keep originals plus a 1024px thumbnail per image (two R2 keys) to keep the kits grid cheap.
- Model kit types as data, not code: a `kit_types` table (id, name, image_slots JSON e.g. [{role:'before',count:3},{role:'after',count:3}] for `transformation`, [{role:'reference',min:1,max:3}] for `heygen`, required metadata fields, delivery template). Kits reference a kit_type_id; the UI renders the uploader and validator from the slot spec. This is what makes the module 'ubiquitous' for future kit/video creators.
- D1 schema to start with: kit_types, kits (id, kit_type_id, persona_name, status, created_by, created_at, updated_at, notes), kit_images (id, kit_id, role, slot_index, r2_key, width, height, bytes, sha256, telegram_file_id), vas (id, name, telegram_chat_id, email), accounts (id UUID, platform, handle, display_name, status, va_id, kit_id, oneup_account_id, sheet_row_key, login_json_encrypted, updated_at, source), kit_assignments (id, kit_id, va_id, sent_at, telegram_message_ids, status), video_jobs (later), sync_runs (source, started_at, rows_in, rows_upserted, errors). Store secrets (bot token, OneUp apiKey, Google SA key JSON) with `wrangler secret put`, never in the sheet or repo.
- Sheet ingestion: use Sheets API v4 with a service account (share the sheet with the SA email as Viewer, later Editor for write-back), one-way Sheet -> D1 on a cron plus a manual 'Sync now' button; add an `account_id` UUID column that the Worker back-fills via values:update so rows survive sorting/insertion; treat the sheet as source of truth for VA-edited fields only, with per-field ownership and last-write-wins by `updated_at`. ## Gotchas

- D1 'rows read' counts rows scanned, not returned: an unindexed `WHERE handle = ?` on a 1,000-row accounts table costs 1,000 reads per call. With a UI that polls, the 5M/day free budget is fine, but add indexes on accounts(platform, handle), accounts(va_id), kit_images(kit_id) from migration 0001. Dashboard/wrangler queries also count.
- D1 free plan allows only 50 queries per Worker invocation and 50 subrequests per request: batch inserts with `db.batch([...])` during sheet import (hundreds of rows) instead of one statement per row, and chunk R2 uploads.
- Free Workers get 10 ms CPU per invocation (including cron). JWT verification with jose, JSON parsing of a few hundred sheet rows and SHA-256 of images usually fit, but image resizing in-Worker will not; generate thumbnails in the browser before upload (canvas) or upgrade to Paid.
- R2 bills usage rounded UP to the next unit (1.1 GB-month -> 2 GB-month) and ListObjects is a Class A op: do not list the bucket to render the kits page; keep image keys in D1.
- Cloudflare Access signing keys rotate every 6 weeks; fetch JWKS at runtime and match `kid`, never hard-code the key. Verify the header (`Cf-Access-Jwt-Assertion`), not the cookie. Once Access is on, any Access login consumes a seat permanently until you remove the user (seat expiration can auto-remove after 1-12 months).
- Telegram webhooks cannot authenticate through Access: you need an Access Bypass policy for the exact webhook path plus the `secret_token` header check; also respond 2xx quickly or Telegram will retry the update.
- Telegram `sendPhoto` recompresses images (bad for reference images meant for AI models); use `sendDocument` for originals, and remember documents can only be grouped with other documents in `sendMediaGroup`. URL-based sends are capped at 5 MB for photos / 20 MB otherwise, multipart at 10 MB / 50 MB, and bots can only DOWNLOAD files up to 20 MB (VA-uploaded images larger than that cannot be pulled back).
- Google Sheets as a database has no row identity: sorting, inserting or deleting rows silently shifts positions. Either back-fill a UUID column or use developer metadata; never key on row number. Publish-to-web CSV is cached (minutes) and requires link-sharing; the gviz endpoint returns JSONP with a prefix you must strip and also requires link-sharing for unauthenticated reads.
- Apps Script web apps answer POST with a 302 redirect and give you no control over CORS headers; browser calls from hq.jwcoconsulting.com must be 'simple' requests (text/plain body, no custom headers) or use no-cors (opaque response). 'Execute as Me + Anyone' turns the deployment URL into a bearer secret; rotate by redeploying.
- Supabase Free projects pause after one week of inactivity and must be manually restored; Storage files are capped at 50 MB on Free; Edge Functions block ports 25/587 and have a 2 s CPU limit.
- GitHub Contents API PUT requires the current file `sha`; two tabs editing accounts.json will produce 409 conflicts; files over 1 MB cannot be read with the default JSON media type (use `raw`), and over 100 MB not at all. Repo history grows with every image commit (1 GB recommended cap).
- Firebase: Cloud Storage now needs a billing account (Blaze) even for free-tier usage; Firestore's document model makes the accounts x kits x assignments joins and ad-hoc SQL migrations awkward for Claude Code.
- Airtable attachment URLs expire after ~2 hours, so a kits UI or Telegram delivery cannot hotlink them; the Free plan's 1,000 API calls/month is roughly 33 page loads a day.
- Facts marked 'likely' (Zero Trust 50-seat free plan, Apps Script quotas, Sheets per-minute quotas, gviz response format, Firebase and Airtable plan numbers, Telegram size limits) were read from search summaries, not the official pages; re-check them on the official URLs before quoting them to the operator.
