# 3. Telegram delivery to VAs

_Research topic: Handing avatar kits to VAs over Telegram (Bot API delivery, chat_id mapping, acknowledgement buttons, Cloudflare Workers webhook hosting, Mini App viewer, secrets handling) and the handoff state machine the HQ site should track_

## Summary

The egress proxy blocks core.telegram.org, grammy.dev, developers.cloudflare.com, docs.aiogram.dev and bitwarden.com, so every Telegram/Cloudflare fact below was read from verbatim mirrors instead: the machine-readable scrape of the Bot API reference (PaulSonOfLars/telegram-bot-api-spec, 'Bot API 10.3, August 24, 2026'), the grammY website and core source on GitHub, aiogram source on GitHub, the Cloudflare docs source repo on GitHub, and the Telegram-Mini-Apps community docs repo. Bitwarden Send and bot privacy mode were only reachable via search snippets and are marked 'likely'.

Delivery: sendMediaGroup takes 2-10 InputMedia items; documents (and audio) may only be grouped with the same type, photos/videos can mix. Photo uploads are capped at 10 MB and are re-encoded by Telegram (lossy), so full-quality reference images must go out as sendDocument / InputMediaDocument (any file type up to 50 MB upload). Captions are 0-1024 chars after entity parsing; message text 1-4096; inline-button callback_data is 1-64 bytes; parse_mode supports HTML and MarkdownV2. Send once by upload, then store the returned file_id (bot-scoped) and re-send by file_id for free. getFile downloads are limited to 20 MB. Flood control: ~1 msg/s per chat, ~20 msg/min per group, 429 + retry_after; use grammY auto-retry.

Mapping VAs: deep link t.me/<bot>?start=<payload>, payload 1-64 chars of [A-Za-z0-9_-]; the /start update gives you from.id (user_id, 52-bit int, store as int64/string) and chat.id, which for a private chat equals the user id. Recommended topology: one private forum supergroup, bot is admin with can_manage_topics, one topic per avatar kit (createForumTopic name 1-128 chars, send with message_thread_id); use DMs only for secrets links. Bot privacy mode (default on) hides non-command group messages unless the bot is admin or replies/mentions are used; buttons (callback_query) are unaffected.

Acks: an inline keyboard under the album's caption-bearing follow-up message (Received / Account created / Need new images), handled via callback_query, answered with answerCallbackQuery (0-200 chars, show_alert) and reflected by editMessageText/editMessageReplyMarkup on the original message. Webhook: Cloudflare Workers via grammY webhookCallback(bot, 'cloudflare-mod', { secretToken }) which checks X-Telegram-Bot-Api-Secret-Token (setWebhook secret_token, 1-256 chars [A-Za-z0-9_-]); grammY's own timeout is 10 s (default onTimeout 'throw'), Telegram retries undelivered updates, so never do slow work inside the webhook (use ctx.waitUntil / Queues / KV). Workers Free: 100k req/day, 10 ms CPU, 50 subrequests; Paid $5/mo, 10M req + 30M CPU-ms included. A Mini App kit viewer is feasible (HTTPS page, launched by inline web_app button in private chats, menu button, or t.me/<bot>/<app>?startapp=<kitId>); validate initData server-side with HMAC-SHA256 (secret = HMAC(bot_token, key 'WebAppData')) plus an auth_date expiry. Never put account passwords in Telegram: send a Bitwarden Send link (text ≤1000 chars, max 31-day lifetime, optional password/access-count limits) or a one-time HQ link instead, and set protect_content on kit media.

## Facts

- **verified** sendMediaGroup: 'Use this method to send a group of photos, live photos, videos, documents or audios as an album. Documents and audio files can be only grouped in an album with messages of the same type.' The media array 'must include 2-10 items'. Returns an Array of Message. Supports message_thread_id, protect_content, disable_notification, reply_parameters. (Read in the verbatim JSON scrape of core.telegram.org/bots/api, 'Bot API 10.3, August 24, 2026'; the primary host is blocked by the proxy.) ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** sendPhoto: 'The photo must be at most 10 MB in size. The photo's width and height must not exceed 10000 in total. Width and height ratio must be at most 20.' Caption 0-1024 characters after entities parsing. Photo can be file_id (recommended), HTTP URL, or multipart upload. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** sendDocument: 'Bots can currently send files of any type of up to 50 MB in size, this limit may be changed in the future.' Caption 0-1024 chars; optional thumbnail (JPEG < 200 kB, max 320x320, only when uploading via multipart); disable_content_type_detection exists and 'Always True, if the document is sent as part of an album' (InputMediaDocument). ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** InputMediaPhoto / InputMediaDocument 'media' field: 'Pass a file_id to send a file that exists on the Telegram servers (recommended), pass an HTTP URL for Telegram to get a file from the Internet, or pass "attach://<file_attach_name>" to upload a new one using multipart/form-data under <file_attach_name> name.' InputMediaPhoto also supports has_spoiler and show_caption_above_media. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **likely** Sending-files size limits when NOT using file_id: 10 MB for photos / 50 MB for other files via multipart upload; 5 MB for photos / 20 MB for other files when Telegram fetches an HTTP URL. (The 'Sending files' prose section is not in the JSON scrape; numbers come from secondary sources quoting it and match the per-method limits above.) ([source](https://fast.io/resources/telegram-file-size-limit/))
- **verified** getFile: 'For the moment, bots can download files of up to 20MB in size.' Download link https://api.telegram.org/file/bot<token>/<file_path> is 'guaranteed ... valid for at least 1 hour'. A self-hosted Bot API server (--local) lifts this: 'Download files without a size limit. Upload files up to 2000 MB.' ([source](https://raw.githubusercontent.com/tdlib/telegram-bot-api/master/README.md))
- **verified** sendMessage text is 1-4096 characters after entities parsing; parse_mode selects the formatting mode (HTML or MarkdownV2 per 'formatting options'); 'entities' can be passed instead of parse_mode. editMessageText has the same 1-4096 limit; editMessageCaption 0-1024. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** InlineKeyboardButton: callback_data is 'Data to be sent in a callback query to the bot when the button is pressed, 1-64 bytes'; url opens 'HTTP or tg:// URL'; web_app (WebAppInfo{url: HTTPS URL}) is 'Available only in private chats between a user and the bot'; copy_text (CopyTextButton, text 1-256 chars) copies text to the clipboard. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** CallbackQuery carries id, from (User), message (MaybeInaccessibleMessage: the bot message that held the button) and data ('Be aware that the message originated the query can contain no callback buttons with this data'). answerCallbackQuery: text 0-200 chars, show_alert bool (alert vs. top-of-chat toast), cache_time seconds, url may be a t.me/your_bot?start=XXXX link. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** editMessageReplyMarkup edits only the inline keyboard of a message; editMessageText / editMessageCaption / editMessageMedia edit content. editMessageMedia on an album item 'can be edited only to ... a document for document albums and to a photo, a live photo, or a video otherwise'. deleteMessage only works for messages sent less than 48 hours ago. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** setWebhook: Telegram POSTs a JSON Update to the HTTPS url; 'In case of an unsuccessful request (a request with response HTTP status code different from 2XY), we will repeat the request and give up after a reasonable amount of attempts.' secret_token: 'A secret token to be sent in a header "X-Telegram-Bot-Api-Secret-Token" in every webhook request, 1-256 characters. Only characters A-Z, a-z, 0-9, _ and - are allowed.' max_connections 1-100 (default 40). allowed_updates e.g. ["message","callback_query"]; empty list = all except chat_member, message_reaction, message_reaction_count. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** createForumTopic: 'Use this method to create a topic in a forum supergroup chat or a private chat with a user. In the case of a supergroup chat the bot must be an administrator in the chat for this to work and must have the can_manage_topics administrator right.' name is 1-128 chars; icon_color must be one of 7322096, 16766590, 13338331, 9367192, 16749490, 16478047. Returns ForumTopic{message_thread_id, name, icon_color}. editForumTopic / closeForumTopic take message_thread_id. All send* methods accept message_thread_id 'for forum supergroups and private chats of bots with forum topic mode enabled only'. Chat.is_forum marks a forum supergroup. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **likely** Bot API 10.x bots can have 'forum topic mode' in private chats (getMe returns has_topics_enabled and allows_users_to_create_topics). A GitHub issue reports that after Bot API 10.0 (May 2026) createForumTopic in private chats can fail with BOT_FORUM_CREATE_FORBIDDEN and sendMessage with message_thread_id can return 'message thread not found' — treat private-chat topics as unstable; use a supergroup forum instead. ([source](https://github.com/tdlib/telegram-bot-api/issues/847))
- **verified** User.id / Chat.id 'may have more than 32 significant bits ... But it has at most 52 significant bits, so a signed 64-bit integer or double-precision float type are safe'. User.can_read_all_group_messages in getMe is 'True, if privacy mode is disabled for the bot'. Update.my_chat_member 'For private chats, this update is received only when the bot is blocked or unblocked by the user' (use it to mark a VA as unreachable). ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** Deep-link /start payload: aiogram's deep_linking helper enforces BAD_PATTERN = [^a-zA-Z0-9-_] and DEEPLINK_PAYLOAD_LENGTH = 64, and offers create_start_link(bot, payload, encode=True) to base64url-encode arbitrary data; also startgroup and startapp link types. Format: https://t.me/<bot_username>?start=<payload>. ([source](https://raw.githubusercontent.com/aiogram/aiogram/dev-3.x/aiogram/utils/deep_linking.py))
- **likely** Bot privacy mode is on by default: in groups the bot only receives commands, replies to its messages and @mentions (plus service messages); disable with BotFather /setprivacy or make the bot an admin, and remove + re-add the bot to existing groups for the change to apply. grammY's docs confirm that forcing a reply ('force_reply') lets the bot receive the user's answer even in privacy mode. (Primary page core.telegram.org/bots/features is blocked.) ([source](https://raw.githubusercontent.com/grammyjs/website/main/site/docs/guide/basics.md))
- **verified** Flood limits quoted by grammY from the Bots FAQ: 'avoid sending more than one message per second' in a particular chat; bulk notifications 'not more than 30 messages per second or so'; 'not ... more than 20 messages per minute to the same group'; plus ~20 message edits per minute per group. Any request may fail with 429 and retry_after; the only correct handling is wait-and-retry (grammY auto-retry plugin; options maxRetryAttempts, maxDelaySeconds; exponential backoff from 3 s for 5xx). ([source](https://raw.githubusercontent.com/grammyjs/website/main/site/docs/advanced/flood.md))
- **verified** grammY webhookCallback options: { onTimeout: 'throw' | 'return' | fn (default 'throw'), timeoutMilliseconds (default 10_000), secretToken } — the adapter reads X-Telegram-Bot-Api-Secret-Token and returns 401 'unauthorized' on mismatch using a constant-time compare. Calling webhookCallback while bot.start() long-polling is running throws. ([source](https://raw.githubusercontent.com/grammyjs/grammY/main/src/convenience/webhook.ts))
- **verified** grammY on Cloudflare Workers (Node/npm): export default { async fetch(request, env, ctx) { const bot = new Bot(env.BOT_TOKEN, { botInfo: JSON.parse(env.BOT_INFO) }); ...; return webhookCallback(bot, 'cloudflare-mod')(request); } }. Pass botInfo (from getMe) so the Worker skips a getMe call per cold request; store BOT_TOKEN with `npx wrangler secret put BOT_TOKEN`, BOT_INFO under [vars] in wrangler.toml; set the webhook with https://api.telegram.org/bot<TOKEN>/setWebhook?url=https://<worker>.<subdomain>.workers.dev/ ; use .dev.vars for local secrets. ([source](https://raw.githubusercontent.com/grammyjs/website/main/site/docs/hosting/cloudflare-workers-nodejs.md))
- **verified** grammY deployment guide: 'Telegram has a timeout for each update that it sends to your webhook endpoint. If you don't end a webhook request fast enough, Telegram will re-send the update' (duplicate processing, bot 'spamming users'); Telegram delivers updates from the same chat sequentially and different chats concurrently; grammY's internal timeout defaults to 10 seconds; setting onTimeout 'return' causes race conditions — the recommended fix is to enqueue slow work (file transfers) and finish the webhook fast. Webhook reply (answering one API call in the HTTP response) is possible via client.canUseWebhookReply but you cannot see errors of that call. (The exact Telegram-side timeout number is not stated by grammY; the '60 s' figure in the task brief is unverified.) ([source](https://raw.githubusercontent.com/grammyjs/website/main/site/docs/guide/deployment-types.md))
- **verified** Cloudflare Workers pricing (docs source): Free plan 100,000 requests/day and 10 ms CPU per invocation; Paid (Standard) $5/month minimum including 10 million requests/month (+$0.30 per additional million) and 30 million CPU-ms/month (+$0.02 per additional million CPU-ms); duration is not billed or limited; subrequests are not billed. ([source](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/workers/platform/pricing.mdx))
- **verified** Cloudflare Workers limits (docs source): Free: 100,000 req/day (Error 1027 when exceeded, resets midnight UTC), 10 ms CPU, 128 MB memory, 50 subrequests/request, 5 cron triggers. Paid: 5 min CPU max (default 30 s, configurable via limits.cpu_ms), 10,000 subrequests, 250 cron triggers. 'There is no hard limit on duration for HTTP-triggered Workers'; waiting on fetch()/KV/D1 does not count as CPU time; only 6 simultaneous connections may be awaiting response headers; outstanding work after the response is cancelled unless passed to ctx.waitUntil(). ([source](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/workers/platform/limits.mdx))
- **verified** Mini App initData validation (aiogram reference implementation, mirrors core.telegram.org/bots/webapps#validating-data-received-via-the-web-app): parse initData as a query string, pop 'hash', build data_check_string = '\n'.join(sorted f'{k}={v}'), secret_key = HMAC_SHA256(key=b'WebAppData', msg=bot_token), expected = HMAC_SHA256(key=secret_key, msg=data_check_string).hexdigest(), compare with constant-time compare. WebAppInitData fields: query_id, user{id, first_name, last_name, username, language_code, is_premium, allows_write_to_pm, photo_url}, receiver, chat, chat_type ('sender'|'private'|'group'|'supergroup'|'channel', direct links only), chat_instance, start_param (also passed as GET param tgWebAppStartParam), can_send_after, auth_date, hash. 'It is empty if the Web App was launched from a keyboard button.' ([source](https://raw.githubusercontent.com/aiogram/aiogram/dev-3.x/aiogram/utils/web_app.py))
- **verified** Third-party (no bot token) initData validation: exclude hash and signature, sort pairs, prepend '<bot_id>:WebAppData\n', verify Ed25519 'signature' (base64url, may need '=' padding) against Telegram's production public key e7bf03a2fa4602af4580703d88dda5bb59f32ed8b02a56c187fe7d34caed242d. Community docs recommend also enforcing an auth_date expiry (e.g. expiresIn: 3600 in @tma.js/init-data-node) and sending initData as `Authorization: tma <raw>`. ([source](https://raw.githubusercontent.com/Telegram-Mini-Apps/telegram-apps/master/apps/docs/platform/init-data.md))
- **verified** Mini App start parameter: passed via t.me/<bot>?startattach=ABC or direct link t.me/<bot>/<appname>?startapp=ABC, surfaces as tgWebAppStartParam and initData.start_param; allowed chars A-Z a-z 0-9 _ -, up to 512 chars (regex /^[\w-]{0,512}$/). Launch parameters arrive in window.location.hash (tgWebAppData, tgWebAppVersion, tgWebAppPlatform, tgWebAppThemeParams) — save them on first load because hash routers can clobber them. Mini App URLs must be HTTPS with a valid certificate (test environment allows raw IPs). ([source](https://raw.githubusercontent.com/Telegram-Mini-Apps/telegram-apps/master/apps/docs/platform/start-parameter.md))
- **verified** Ways to launch a Mini App from the Bot API: InlineKeyboardButton.web_app (private chats only; can answerWebAppQuery), KeyboardButton.web_app (private chats; returns a 'web_app_data' service message, i.e. Message.web_app_data{data, button_text} — 'a bad client can send arbitrary data in this field'), and the chat menu button MenuButtonWebApp{type:'web_app', text, web_app} which may also hold a t.me link to the app. ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** file_id semantics (grammY guide): every file the bot sends or receives yields a file_id that can be reused 'as often as you want' to resend without uploading; file_ids are bot-scoped (a friend's bot's file_id may stop working); the same file can have several file_ids, so compare file_unique_id to detect duplicates; getFile URLs expire after about 60 minutes. ([source](https://raw.githubusercontent.com/grammyjs/website/main/site/docs/guide/files.md))
- **likely** Photos sent as 'photo' (sendPhoto / InputMediaPhoto) are re-encoded and downscaled by Telegram (commonly ~1280 px longest edge in clients, lossy JPEG); sending as a document ('file') preserves the original bytes but shows no inline preview. (General Telegram behaviour from secondary sources; core.telegram.org does not state the exact pixel limit.) ([source](https://rfgcreative.com/misc/how-to-send-picture-with-text-in-telegram.html))
- **likely** Bitwarden Send (help article via search snippet): maximum file size per Send is 500 MB (100 MB on mobile) and file Sends require Premium plus a verified email; text Sends hold up to 1,000 characters (after ~30-50% encryption growth); deletion date defaults to 7 days and the maximum is 31 days from creation; optional expiration date, maximum access count and password are available. Primary host bitwarden.com is blocked by the proxy. ([source](https://bitwarden.com/help/create-send.md))
- **verified** protect_content (on sendMessage/sendPhoto/sendDocument/sendMediaGroup/copyMessage) 'Protects the contents of the sent message(s) from forwarding and saving'; Message.has_protected_content reflects it. Useful to stop VAs re-forwarding kit images, at the cost of them not being able to save to the gallery (they can still screenshot). ([source](https://raw.githubusercontent.com/PaulSonOfLars/telegram-bot-api-spec/main/api.json))
- **verified** Webhook security per aiogram docs: 'Always set and verify X-Telegram-Bot-Api-Secret-Token'; IP allow-listing is secondary and X-Forwarded-For is only trustworthy behind a trusted reverse proxy. Telegram also suggests a secret path such as https://example.com/<token> if secret_token is not used. ([source](https://raw.githubusercontent.com/aiogram/aiogram/dev-3.x/docs/dispatcher/webhook.rst))

## Recommendations

- TOPOLOGY: create one private forum supergroup ('JWCo Kits'), add the bot as admin with can_manage_topics + can_delete_messages + can_pin_messages, invite each VA. For every kit the HQ site calls createForumTopic(name=`${kit.code} - ${kit.persona}`) and stores kit.telegram_thread_id; all kit messages go to that thread via message_thread_id. VAs get a separate private DM with the bot (via deep link) that is used only for sensitive links and per-person nudges. Reason: one place for the whole history per avatar, admin can see everything, no privacy-mode surprises for bot-sent messages, and the thread id is a stable foreign key. Treat Bot API 10.x 'topics in private chats' as experimental (reported breakage) and do not rely on it.
- VA ENROLLMENT: HQ generates a deep link https://t.me/<bot>?start=va_<vaId>_<nonce> (payload must be [A-Za-z0-9_-], <=64 chars; nonce single-use, expires in 24h). On the /start update the Worker stores vas[vaId].telegram_user_id = from.id (int64, keep as string in JS/JSON), .chat_id = chat.id (== user id for DMs), .username, .enrolled_at, then replies with a welcome + the current kit list. Table: vas{id, name, telegram_user_id, dm_chat_id, username, status: invited|enrolled|blocked, invite_payload, invite_expires_at}. Mark status=blocked when an Update.my_chat_member in the DM shows the bot was blocked.
- KIT HANDOFF MESSAGE LAYOUT (3 messages, all into the kit's topic, all with protect_content=true): (1) sendMediaGroup of InputMediaPhoto items (2-10; a transformation kit = 6 photos, a HeyGen kit = 1-3 photos plus an optional 1-2 'look' shots) by file_id (upload once with attach:// on first send, persist each returned photo[-1].file_id and file_unique_id on kit.images[]). Caption only on the FIRST item (<=1024 chars, parse_mode=HTML): '<b>Kit EMR-01 Emerson</b> - transformation (3 before / 3 after)\nPersona: ... Age/vibe: ... Handle to create: @...\nPlatform: TikTok + IG\nDeadline: ...'. (2) sendMediaGroup of the SAME images as InputMediaDocument (full-resolution originals, filenames like emr-01_before_1.png) - documents cannot be mixed with photos in one album, hence the second album; skip it for HeyGen kits if the previews are already final quality. (3) sendMessage 'control card' (HTML, <=4096 chars) holding the checklist (account email alias, DOB to use, bio text, link-in-bio, profile pic = image #N, OneUp category) and an InlineKeyboardMarkup with rows [['Received'],['Account created'],['Need new images']] plus an optional url/web_app button 'Open kit in HQ'. callback_data format: `k:<kitId>:<action>` (<=64 bytes; use short kit ids). Store the three message_ids on kit_handoffs[] so later edits/replies target the control card.
- ACK FLOW: handle update.callback_query; verify callback_query.from.id matches the assigned VA (or is the operator), parse data, write the transition, call answerCallbackQuery(text='Thanks, marked received', show_alert=false) within the webhook, then editMessageText on the control card to render the status line ('Status: ACCOUNT CREATED by @va at 14:02') and editMessageReplyMarkup to show only the next valid buttons (after 'Account created' show ['Post handle'] and a 'Need new images' button; after 'Need new images' send a force_reply prompt asking what is wrong and treat the reply as the reason). Always answer the callback even on error to stop the client spinner. Keep an audit row per transition: {kit_id, va_id, from_state, to_state, actor_telegram_id, message_id, ts, note}.
- STATE MACHINE for kit_handoffs (and derived kit.status): draft -> queued (operator pressed Send in HQ; Worker job created) -> sent (Telegram returned message ids; store them) -> delivered? (no read receipts in Bot API - skip) -> acknowledged ('Received' pressed) -> in_progress (optional: VA pressed 'Started') -> account_created ('Account created' pressed; VA then replies with the handle, bot parses @handle and stores accounts[]) -> verified (operator confirms in HQ that the account exists, links OneUp social account id) -> active (first post scheduled). Side branches: needs_new_images (from any state after sent; returns to draft of a new kit version, old handoff -> superseded), expired (no ack after N days, re-nudge in DM), revoked (operator pulled it; delete control card if <48h, else edit it to 'REVOKED'), failed (send error / 429 exhausted). Persist version numbers so a re-sent kit creates a new handoff row rather than overwriting.
- WORKER DESIGN (Cloudflare, grammY): routes POST /tg/webhook (webhookCallback(bot,'cloudflare-mod',{secretToken: env.TG_WEBHOOK_SECRET})), POST /api/kits/:id/send (HQ -> Worker, bearer-auth; validates and enqueues), and a Queue consumer or ctx.waitUntil that performs the 3 sends sequentially with the auto-retry transformer (maxDelaySeconds ~30) and writes results to D1/KV. Call setWebhook once with url, secret_token (random 32+ chars [A-Za-z0-9_-]), allowed_updates=['message','callback_query','my_chat_member'], drop_pending_updates on first deploy. Keep webhook handlers under grammY's 10 s default; a kit send with two 6-item albums fits comfortably when images are sent by file_id, but first-time uploads (6 x multi-MB PNGs) should run in the queue/waitUntil path, not inside the Telegram webhook. Free plan suffices for this volume (100k req/day, 50 subrequests/invocation covers 3 API calls per send); move to Paid ($5/mo) only if CPU >10 ms per request becomes an issue (e.g. image processing - do that elsewhere).
- IMAGE QUALITY: use photo albums for the preview the VA will actually look at on a phone, and document albums (or a zip as one sendDocument <=50 MB) for originals needed to create the account avatar / HeyGen reference. Pre-generate 1080px JPEG previews in HQ so photo uploads stay well under 10 MB and under the 10000-px combined dimension rule. For images hosted on R2/Drive, prefer uploading bytes (10/50 MB) over the URL path (5/20 MB) and to avoid Telegram fetch failures on signed URLs.
- SECRETS: never put account passwords, 2FA seeds or email passwords in a Telegram message or caption. Options in order: (a) a Bitwarden Send text item (<=1000 chars, password-protected, max access count 1-2, deletion date <=31 days) whose URL goes to the VA's DM, not the group topic; (b) an HQ one-time link (/secret/<token>, 15-min TTL, single view, logged) behind Cloudflare Access; (c) a shared Bitwarden/1Password collection per VA. Put the Send/HQ link under a url button labelled 'Open credentials (expires in 24h)'. Turn on protect_content for kit media; rotate the bot token if it ever appears in logs; keep the secret_token in a Worker secret, not wrangler.toml [vars].
- MINI APP VIEWER (phase 2): host a tiny HTTPS page on the same Worker (/tma/kit?kit=<id>), launch it from an inline web_app button in the VA's DM (web_app buttons do not work in groups) or via direct link t.me/<bot>/kit?startapp=<kitId> (<=512 chars [A-Za-z0-9_-]), and from the chat menu button. The page sends `Authorization: tma <initDataRaw>` to the Worker, which validates HMAC-SHA256 (secret = HMAC(bot_token, key 'WebAppData')) and rejects auth_date older than 1 h, then checks initData.user.id against vas.telegram_user_id before serving the kit JSON/images. Worth it when VAs need to tick checklists or paste handles with validation; not needed for v1 where buttons + replies suffice.
- HQ UI HOOKS: on the kit page show a 'Telegram' panel: assigned VA, topic link (https://t.me/c/<internal_id>/<thread_id>), last handoff state + timestamp, button 'Send to VA' (disabled until VA is enrolled and kit has >=2 preview images), 'Nudge' (sends a DM reply referencing the control card), and the audit trail. On the Accounts page, when a VA reports a handle, auto-create the account row in state 'reported' and surface a 'Link to OneUp social account' action that matches OneUp listsocialaccounts by handle.

## Gotchas

- All primary Telegram/Cloudflare/Bitwarden hosts (core.telegram.org, grammy.dev, developers.cloudflare.com, docs.aiogram.dev, bitwarden.com) are blocked by this session's egress proxy; the facts here were read from verbatim mirrors (the JSON scrape of the Bot API reference labelled 'Bot API 10.3, August 24, 2026', grammY/aiogram/Cloudflare-docs GitHub sources). Re-check the canonical pages before implementation.
- sendMediaGroup cannot mix documents with photos: full-quality originals (documents) and previews (photos) must be two separate albums or a single zip document. Each album is 2-10 items, so a kit with 1 image cannot use an album - send a single sendPhoto/sendDocument instead and branch on image count.
- Only the first album item's caption is displayed as the album caption in clients when exactly one item has a caption; captions on every item make the album show no shared caption. Keep the kit summary in the first item or in a separate control message.
- Inline keyboards cannot be attached to sendMediaGroup messages (no reply_markup parameter), which is why the buttons live on a separate control message. Keep that message's message_id to edit status later.
- callback_data is 1-64 bytes; put ids, not JSON, in it. The callback_query.message may be 'inaccessible' (MaybeInaccessibleMessage) for old messages; do not assume message.text is present.
- Photo re-encoding: anything sent via sendPhoto/InputMediaPhoto is compressed and downscaled by Telegram; VAs who upload that as a profile picture will get a lower-quality avatar. Send documents for anything that must be pixel-exact (HeyGen reference images especially).
- file_ids are bot-scoped and can change; store file_unique_id for dedupe and keep the original object in R2/Drive as the source of truth. Downloads via getFile are capped at 20 MB (no issue for sending).
- Telegram retries any webhook request that does not get a 2xx fast enough; with grammY's default 10 s timeout a slow first-time upload inside the webhook will cause duplicate sends. Do uploads in ctx.waitUntil()/Queues and make handlers idempotent on update_id.
- Flood control: 1 msg/s per chat, 20 msg/min per group, ~20 edits/min per group; a kit send is 3 messages so sending many kits into the same forum group at once will hit 429 - serialize per group and honour retry_after (auto-retry plugin). Cloudflare Free allows only 50 subrequests per invocation and 6 concurrent connections awaiting headers.
- Bot privacy mode (default on) means the bot will NOT see a VA's free-text reply in the group unless it is a reply to the bot's message, an @mention, or the bot is an admin; use force_reply prompts or make the bot admin. Buttons (callback_query) always reach the bot.
- Forum topic mode in private chats (Bot API 10.x) has a reported regression (createForumTopic BOT_FORUM_CREATE_FORBIDDEN, 'message thread not found'); stick to a forum supergroup for topics.
- web_app inline buttons only work in private chats, not in the group topic; a Mini App viewer must be launched from the VA's DM, the menu button, or a t.me/<bot>/<app>?startapp= link. initData is empty when the Mini App is opened from a reply-keyboard button, and Message.web_app_data can be forged by a bad client - only trust server-validated initData.
- deleteMessage works only within 48 h; after that, 'revoke' must be an edit (strip buttons, replace caption) rather than a delete. editMessageMedia on an album can only swap like-for-like media types.
- protect_content stops forwarding/saving but not screenshots; it also prevents the VA from saving images to their camera roll, which they may need for account creation - decide per kit type, or send originals as documents without protection and previews with it.
- Bitwarden file Sends require a Premium plan and verified email; text Sends are limited to 1,000 characters (grows 30-50% when encrypted) and expire within at most 31 days - fine for passwords, not for image kits.
- The '60 s webhook response rule' in the task brief could not be verified on any reachable source; grammY only says Telegram 'has a timeout' and resends. Design for <10 s regardless.
