# 2. HeyGen avatars and the HeyGen kit

_Research topic: HeyGen avatars: what a 'HeyGen avatar kit' must contain (photo avatars, avatar groups, looks, Avatar IV, v2/v3 endpoints, limits, consent)_

## Summary

Research caveat: the egress proxy blocks docs.heygen.com, developers.heygen.com, help.heygen.com, www.heygen.com and web.archive.org, so no HeyGen-hosted page was read directly. Facts below come from (a) HeyGen's own GitHub repos read raw (heygen-com/skills, heygen-com/openclaw-plugin-heygen), (b) a community mirror of HeyGen's OpenAPI spec (api-evangelist/heygen) and a saved copy of the docs.heygen.com 'limits' page (fracabu/heygen-app, dated 2025-11-26), (c) third-party SDKs that transcribe developers.heygen.com v3 schemas (corsairdev/corsair, apollographql/connectors-community, davila7/claude-code-templates), and (d) search-result snippets. Nothing is marked 'verified' unless read from a HeyGen-authored source.

Key model: a HeyGen photo avatar is anchored by an AVATAR GROUP (group_id) that is created from exactly ONE image (image_key from the upload-asset API, or a generated photo's generation_id+image_key). More images of the same subject are added as LOOKS (max 4 image_keys per 'add looks' call, up to 500 looks per group). The group must be TRAINED (4 credits, status polled at /v2/photo_avatar/train/status/{group_id}) before new looks can be generated from a text prompt (/v2/photo_avatar/look/generate, 1 credit). Each look is itself a 'photo avatar' with its own id; add_motion (1 credit) and upscale (0.5 credit, only on a motion avatar) each return a NEW avatar id. Video is produced either via Avatar IV (POST /v2/video/av4/generate with an image_key/photo_s3_key of a still + script + voice_id, 6 credits/min on the API plan table) or via /v2/video/generate with character.type='talking_photo' + talking_photo_id (1 credit/min). HeyGen's own skill files say look_ids are ephemeral and must be re-resolved from group_id at runtime, so the kit's durable anchor is group_id + voice_id + the original reference image files, not look ids.

The newer v3 API (developers.heygen.com) replaces the v2 group/train/look flow with POST /v3/avatars where type is 'photo' (one file), 'prompt' (text prompt + up to 3 reference_images) or 'digital_twin' (real person, consent required); GET /v3/avatars/looks?group_id=... lists looks with preview_image_url, image_width/height and preferred_orientation. The operator's 'one to three good reference images' maps exactly onto v3 type='prompt' with reference_images (max 3), which is the recommended path for new HeyGen kits. Consent: HeyGen states photo avatars and prompt-to-avatar characters depict no real identifiable person and do not require consent; only digital twins do. 'HeyGen Bible' is not a HeyGen product or API term; it is almost certainly the friend's own name for a persona/prompt playbook page in their reel-studio app.

## Recommendations

- Kit type 'heygen' - minimal and complete field list (store in the kit record; everything below 'provider' is HeyGen-specific):
- kit_id, kit_type:'heygen', persona_id (FK to persona: name, age band, gender, ethnicity, hair, build, features, style, voice tone/accent/energy - same vocabulary as HeyGen's AVATAR-<NAME>.md)
- reference_images[1..3]: {local_path or R2/Drive URL, sha256, width, height, mime, role:'primary'|'alt', framing:'close_up'|'half_body'|'full_body', orientation:'portrait'|'landscape'|'square', heygen_asset_id?, heygen_image_key?} - the ORIGINAL files are the durable truth; HeyGen asset ids/keys are a cache
- appearance_prompt (max 1000 chars; used for v3 type='prompt' or v2 photo/generate appearance) and look_prompt_defaults {pose, style, orientation}
- heygen.api_version:'v3'|'v2'
- heygen.group_id (stable anchor), heygen.group_name, heygen.avatar_type ('photo'|'prompt'), heygen.train_status / status, heygen.consent_status (should be n/a for photo/prompt)
- heygen.voice_id, voice_name, voice_designed (bool), voice_seed?
- heygen.looks[]: {look_id, name, source:'uploaded'|'generated'|'motion'|'upscaled', parent_look_id?, image_key, preview_image_url, image_width, image_height, preferred_orientation, is_motion, upscaled, status, created_at} - treat as a refreshable cache keyed by group_id
- heygen.default_look_by_orientation {portrait: look_id, landscape: look_id, square: look_id}
- heygen.talking_photo_id? (only if the legacy /v2/video/generate path is used)
- heygen.last_synced_at, heygen.account_label (which HeyGen login/API key owns the group - groups are per-account and plan-capped at 3/10/unlimited)
- cost_log[]: {action, credits_or_usd, at} so the UI can show spend like the friend's 'YOUR RUN' rail
- va_handoff: {telegram_chat_id, sent_at, package_version} and accounts_created[] (links to the Accounts table)
- Numbered HeyGen avatar creation workflow (v3-first, with v2 fallback):
1. Author the persona (name, demographic enums, appearance prompt <=1000 chars, voice brief) in the Kit UI; save as kit draft.
2. Pick or make 1-3 reference images. Validate locally before upload: one face, both eyes visible, >=512x512 (prefer >=1080p), JPEG/PNG, <10 MB (<32 MB for v3 assets), crop to the orientation you will mostly post (9:16 for Reels/TikTok).
3. Upload each image: POST /v3/assets (multipart 'file') -> asset_id; or legacy POST https://upload.heygen.com/v1/asset (raw body, Content-Type image/jpeg|png) -> image_key. Store both ids on the kit image record.
4. Create the avatar group: v3 POST /v3/avatars {type:'prompt', name, prompt, reference_images:[<=3 asset refs]} (or type:'photo' with one file) -> data.avatar_group.id + data.avatar_item.id. v2 fallback: POST /v2/photo_avatar/avatar_group/create {name, image_key} -> group_id, then POST /v2/photo_avatar/avatar_group/add {group_id, image_keys:[<=4], name} for the other reference images.
5. (v2 only) POST /v2/photo_avatar/train {group_id} (4 credits); poll GET /v2/photo_avatar/train/status/{group_id} until status is ready; record train_status. For v3, poll GET /v3/avatars/{group_id} / looks until status is completed and preview_image_url is non-null.
6. Choose a voice: GET /v3/voices (or /v2/voices) and store voice_id + name; optionally design a voice and store the seed.
7. Generate extra looks on demand: v2 POST /v2/photo_avatar/look/generate {group_id, prompt, orientation, pose, style} (1 credit) -> poll GET /v2/photo_avatar/generation/{generation_id} -> image_key_list; add them with avatar_group/add. v3: POST /v3/avatars {type:'prompt', avatar_group_id, prompt, reference_images}.
8. Optionally POST /v2/photo_avatar/add_motion {id} (1 credit, returns NEW id), POST /v2/photo_avatar/add_sound_effect {id} (free), POST /v2/photo_avatar/upscale {id} (0.5 credit, motion avatar only, returns NEW id). Store each returned id as a new look row with parent_look_id.
9. Sync: GET /v3/avatars/looks?group_id=... (or /v2/avatar_group/{group_id}/avatars) and overwrite heygen.looks[]; set last_synced_at. Do this before every video run because look ids are treated as ephemeral.
10. Test render: POST /v2/video/av4/generate {image_key, script, voice_id, video_orientation:'portrait', video_title} (6 credits/min, 30 s billing increments) -> video_id; poll /v1/video_status.get. Mark kit status 'ready' only after a successful test.
11. Package for the VA: zip the original reference images + a persona sheet (name, bio, handle suggestions, voice, do/don't list) and send over Telegram (sendMediaGroup for 2-10 photos; documents separately). Record va_handoff.
- Make 'kit_type' a first-class discriminator with a per-type JSON schema: transformation kits need image_role in {before,after} x 3 each; heygen kits need 1-3 reference images + the heygen block above. The UI's 'Create kit' wizard should branch on kit_type at step 1 and the 'adjust this with Claude' button should hand Claude the schema file for that type.
- Prefer the v3 API for new kits (single POST /v3/avatars with up to 3 reference_images matches the operator's mental model exactly) but keep a v2 adapter because the look/motion/upscale/sound-effect operations are only documented on v2 today.
- Store the operator's original reference images in storage the HQ site controls (R2/Drive) and keep HeyGen ids as a cache; HeyGen assets 'may face deletion after prolonged inactivity' per a community mirror, and look ids are explicitly described as ephemeral by HeyGen's own skill.
- Show live cost in the run rail using the credit table (train 4, look 1, motion 1, upscale 0.5, Avatar IV 6/min billed per 30 s) but label it 'from HeyGen docs snapshot 2025-11' and let the operator override the per-unit price in settings, since 2026 third-party sources describe a USD-wallet model instead.

## Gotchas

- All HeyGen-hosted documentation (docs.heygen.com, developers.heygen.com, help.heygen.com, www.heygen.com) and web.archive.org are blocked by this session's egress proxy; every endpoint/field here comes from HeyGen's GitHub repos or community mirrors of the docs. Re-verify the Avatar IV field name (image_key vs photo_s3_key) and the current price table against the live docs before coding.
- A v2 avatar group is created from exactly ONE photo; more photos are 'looks' added afterwards (max 4 image_keys per add call). Do not try to pass 3 images to avatar_group/create.
- Look generation requires the group to be trained first (train = 4 credits, async). Untrained groups will reject /v2/photo_avatar/look/generate.
- add_motion and upscale return NEW avatar ids; the kit must track parent/child look ids or the UI will lose the upgraded version. Upscale only works on a look that already has motion.
- HeyGen's own skill says look_ids are ephemeral and must be re-resolved from group_id at runtime; the durable kit anchor is group_id + voice_id + your own copies of the reference images.
- v3 responses are a flat {data} (lists: {data, has_more, next_token}); v2 responses are {error, data}. A single client must handle both envelopes.
- Avatar groups are capped per plan on the saved limits page (Free 3, Pro 10, Scale unlimited) and looks per group at 500; a fleet of personas may need the Scale plan or multiple HeyGen accounts, so the kit should record which account owns the group.
- Orientation mismatch (portrait look -> landscape video) produces bars/odd framing; HeyGen's video skill handles it by annotating the prompt. Store looks per orientation and pick the matching one.
- Pricing conflict: the 2025-11 limits snapshot says Avatar IV = 6 credits/min on API plans, while 2026 third-party pages describe a USD wallet (~$0.05-0.10/s) and 20 credits/min on Studio plans. Do not hardcode prices.
- Consent: photo/prompt avatars need no consent, but the moderation policy forbids avatars of real people without consent and impersonation; if any reference image is of a real person (even stock), the kit should record its source/license.
- 'HeyGen Bible' is not a HeyGen term; do not design around it as if it were an API object.
